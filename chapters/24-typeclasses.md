# Классы типов

В прошлой главе мы поднимались и опускались на лифте между этажами нашего типового небоскрёба, и я обещал вам, что не все этажи одинаковы. Но прежде чем разбираться, чем один этаж отличается от другого, нам нужно освоить ещё один важный инструмент &mdash; классы типов (англ. type classes). Без них невозможно по-настоящему понять ни `Functor`, ни `Monad`, ни вообще львиную долю идиоматичного Haskell-кода. Что ж, засучим рукава.

## Проблема одинакового имени

Начнём с конкретной задачи. У нас есть два типа, оба уже знакомые нам по прошлым главам:

```haskell
data IPAddress = IPAddress String

data EndPoint = EndPoint IPAddress Int
```

Мы хотим для каждого из них получить человекочитаемое описание &mdash; строку, которую можно, скажем, вывести в лог. Ничего сложного, определим по функции для каждого типа:

```haskell
describeIP :: IPAddress -> String
describeIP (IPAddress addr) = "IP-адрес: " ++ addr

describeEndPoint :: EndPoint -> String
describeEndPoint (EndPoint ip port) =
    describeIP ip ++ ", порт: " ++ show port
```

Работает? Работает. Но обратите внимание на кое-что: нам пришлось придумывать разные имена для, по сути, одной и той же операции &mdash; &laquo;опиши мне значение этого типа&raquo;. `describeIP`, `describeEndPoint`&hellip; А если у нас таких типов будет двадцать? Тридцать? Каждый раз выдумывать новое имя &mdash; занятие, прямо скажем, безрадостное. Хочется написать один раз функцию с именем `describe`, а дальше просто вызывать её с любым нашим типом:

```haskell
main :: IO ()
main = do
    putStrLn $ describe someIP
    putStrLn $ describe someEndPoint
```

Один и тот же вызов `describe`, но применяется он к значениям совершенно разных типов, и в зависимости от типа значения должно происходить разное поведение. В большинстве императивных языков это называется перегрузкой функций (англ. function overloading) или полиморфизмом. Но у нас уже есть полиморфизм! Мы встречали его, например, в функции `length`:

```haskell
length :: [a] -> Int
```

Эта функция работает решительно с любым списком, вне зависимости от типа элементов. Так почему бы не написать `describe` точно так же?

```haskell
describe :: a -> String
describe x = ???
```

Вот тут-то и кроется загвоздка. Внутри функции `describe` нам нужно как-то по-разному обработать `IPAddress` и `EndPoint`, а типовая заглушка `a` в объявлении означает буквально следующее: &laquo;эта функция ничего не знает о типе своего аргумента, кроме того, что он существует&raquo;. Загляните ещё раз на функцию `length`: ей совершенно неважно, что за элементы в списке, она их даже не разглядывает, знай себе считает ячейки. И именно поэтому она может быть настолько полиморфной. А вот `describe`, наоборот, обязана знать тип, чтобы решить, как именно формировать строку. Тут одной лишь типовой заглушки маловато.

## Два вида полиморфизма

Пришло время развести два похожих, но всё же разных явления.

Тот полиморфизм, что мы видели в `length`, `head`, `map` и прочих подобных функциях, называется параметрическим полиморфизмом (англ. parametric polymorphism). Его девиз можно сформулировать так: &laquo;мне неважно, что там за тип, я работаю одинаково для всех&raquo;. Функция `length` определена ровно один раз, и это определение годится решительно для любого типа элементов списка.

А вот то, что нам нужно для `describe`, называется полиморфизмом ad hoc (англ. ad hoc polymorphism), или же перегрузкой (англ. overloading). Его девиз прямо противоположный: &laquo;для каждого типа &mdash; своё собственное поведение&raquo;. Функция как бы одна, но под капотом &mdash; разные реализации для разных типов.

```
параметрический полиморфизм:

    length :: [a] -> Int         одна реализация на все типы

полиморфизм ad hoc:

    describe :: a -> String      разные реализации для разных типов,
                                  но одно и то же имя
```

В Haskell за реализацию полиморфизма ad hoc отвечают классы типов. Забегая вперёд, скажу: несмотря на слово &laquo;класс&raquo;, ничего общего с классами из объектно-ориентированных языков тут нет. Ни наследования в привычном смысле, ни объектов, ни инкапсуляции данных. Класс типов &mdash; это, по сути, контракт: набор функций, которые обязан реализовать тип, если он хочет &laquo;вступить&raquo; в этот класс.

## Определяем свой класс

Определим класс типов `Describable`:

```haskell
class Describable a where
    describe :: a -> String
```

Читается это так: &laquo;класс типов `Describable` определяет типовую заглушку `a`, и всякий тип, который захочет быть представителем этого класса, обязан предоставить функцию `describe` с сигнатурой `a -> String`&raquo;. Обратите внимание, здесь мы видим только сигнатуру, но не реализацию &mdash; это ожидаемо, ведь класс лишь описывает контракт, а не выполняет его.

Теперь нужно объявить, что наши типы &mdash; представители (англ. instance) этого класса, и предоставить для каждого свою реализацию:

```haskell
instance Describable IPAddress where
    describe (IPAddress addr) = "IP-адрес: " ++ addr

instance Describable EndPoint where
    describe (EndPoint ip port) =
        describe ip ++ ", порт: " ++ show port
```

Взгляните, как изящно здесь сработала перегрузка: внутри реализации `describe` для `EndPoint` мы вызываем `describe ip`, и компилятор точно знает, что нужно взять реализацию именно для `IPAddress`, потому что тип значения `ip` ему известен. Никакой путаницы.

Теперь наш `main` из начала главы прекрасно компилируется и работает:

```haskell
main :: IO ()
main = do
    putStrLn $ describe someIP        -- сработает describe для IPAddress
    putStrLn $ describe someEndPoint  -- сработает describe для EndPoint
  where
    someIP       = IPAddress "192.168.0.1"
    someEndPoint = EndPoint someIP 8080
```

Компилятор сам решает, какую именно реализацию `describe` подставить, глядя на тип аргумента. Это называется диспетчеризацией по типу (англ. type dispatch), и происходит она целиком во время компиляции, без какого-либо оверхеда в рантайме &mdash; в отличие, скажем, от виртуальных методов в ООП-языках.

## Ограничения типов

А что, если мы захотим написать функцию, которая принимает &laquo;что угодно, лишь бы оно было представителем `Describable`&raquo;? Такое тоже возможно, и вот как это выглядит:

```haskell
describeAll :: Describable a => [a] -> String
describeAll xs = concatMap (\x -> describe x ++ "\n") xs
```

Взгляните на сигнатуру повнимательнее:

```haskell
describeAll :: Describable a => [a] -> String

                ограничение    собственно
                типа           сигнатура функции
```

Часть до знака `=>` называется ограничением типа (англ. type constraint, или же class constraint). Она гласит: &laquo;типовая заглушка `a` может быть любым типом, но только при условии, что этот тип является представителем класса `Describable`&raquo;. Это своего рода компромисс между параметрическим полиморфизмом и полиморфизмом ad hoc: функция `describeAll` полиморфна (работает с любым `a`), но не абсолютно &mdash; у типа `a` обязана быть определённая возможность, а именно возможность быть описанным через `describe`.

Если вы попробуете вызвать `describeAll` со списком значений типа, который не является представителем `Describable`, компилятор откажется компилировать программу и честно сообщит вам об этом:

```bash
No instance for (Describable SomeOtherType)
  arising from a use of ‘describeAll’
```

Это прекрасный пример философии Haskell в действии: ошибка, которая во многих других языках всплыла бы только во время выполнения программы (а то и вовсе осталась бы незамеченной), здесь отлавливается ещё на этапе компиляции.

## Стандартные классы типов

Вы уже пользовались классами типов, даже не подозревая об этом. Вспомните оператор `==`:

```haskell
Prelude> 5 == 5
True
Prelude> "haskell" == "haskell"
True
```

Он работает и для чисел, и для строк, и для списков, и для кортежей &mdash; для великого множества типов. Но реализован он для каждого типа по-своему: сравнение чисел &mdash; это одно, а сравнение строк (то есть списков символов, если помните) &mdash; совсем другое, поэлементное сравнение. Всё это работает благодаря стандартному классу типов `Eq`:

```haskell
class Eq a where
    (==) :: a -> a -> Bool
    (/=) :: a -> a -> Bool
```

Если мы захотим сравнивать значения нашего типа `IPAddress` на равенство, нужно сделать его представителем `Eq`:

```haskell
instance Eq IPAddress where
    (IPAddress a1) == (IPAddress a2) = a1 == a2
    ip1            /= ip2            = not (ip1 == ip2)
```

Обратите внимание: реализовав `==`, мы могли бы вовсе не реализовывать `/=` &mdash; у класса `Eq` есть реализация по умолчанию (англ. default implementation) для `/=`, выраженная через `==`. Это довольно частая практика в определении классов типов: одну функцию сделать обязательной, а другую вывести из неё автоматически, чтобы избавить представителей класса от лишней писанины.

Но постойте, разве мы уже не видели способ попроще? Ну конечно, `deriving`:

```haskell
data IPAddress = IPAddress String deriving (Eq)
```

Мы встречали эту конструкцию раньше, когда учились определять свои типы, но тогда я попросил вас поверить мне на слово. Теперь же, вооружившись знанием о классах типов, я могу сказать честно: `deriving (Eq)` &mdash; это просьба к компилятору автоматически сгенерировать для нас представителя класса `Eq`, точно такого же, какого мы написали бы вручную. Для простых типов вроде `IPAddress`, где сравнение сводится к сравнению внутренних полей, компилятор прекрасно справляется сам, и незачем утруждать себя самостоятельным написанием очевидного кода.

То же самое относится к другим часто встречающимся классам:

```haskell
data IPAddress = IPAddress String
    deriving (Eq, Ord, Show)
```

Класс `Ord` (от англ. order, &laquo;порядок&raquo;) даёт нам операторы сравнения `<`, `>`, `<=`, `>=`, а также функцию `compare`, и позволяет, например, сортировать список значений вашего типа. А класс `Show`, который мы использовали множество раз, даже не задумываясь, отвечает как раз за функцию `show`, превращающую значение в строковое представление:

```haskell
class Show a where
    show :: a -> String
```

Всякий раз, когда GHCi показывает вам результат вычисления в консоли, за кулисами работает именно `show`. Вот почему для типов без `deriving (Show)` GHCi откажется что-либо печатать:

```bash
No instance for (Show IPAddress)
  arising from a use of ‘print’
```

Компилятор словно бы говорит нам: &laquo;я понятия не имею, как превратить значение этого типа в строку, ты не научил меня этому&raquo;. И он совершенно прав &mdash; такова цена полиморфизма ad hoc: каждый тип обязан явно заявить о своих способностях.

## Классы классов

Могут ли классы типов зависеть друг от друга? Разумеется. Взгляните на настоящее определение класса `Ord` из стандартной библиотеки, слегка упрощённое:

```haskell
class Eq a => Ord a where
    compare :: a -> a -> Ordering
    (<)     :: a -> a -> Bool
    (>)     :: a -> a -> Bool
```

Часть `Eq a =>` здесь называется суперклассом (англ. superclass). Она означает: &laquo;чтобы тип `a` мог стать представителем класса `Ord`, он обязан сперва быть представителем класса `Eq`&raquo;. Логика тут прозрачна: как можно сравнивать значения на &laquo;больше&raquo; или &laquo;меньше&raquo;, если мы даже не умеем проверять их на равенство? Порядок &mdash; понятие более богатое, чем равенство, и потому строится поверх него.

```
        Eq
        |
        | суперкласс для
        v
       Ord
```

Именно поэтому `deriving (Ord)` без `Eq` попросту не скомпилируется:

```haskell
data Priority = Low | Medium | High
    deriving (Ord)  -- Ошибка!
```

```bash
No instance for (Eq Priority)
  arising from the superclasses of an instance declaration
```

Компилятор напоминает нам про иерархию, установленную классами типов: прежде чем подниматься по лестнице возможностей, нужно освоить нижние ступени.

## Зачем нам всё это

Вы вправе спросить: а зачем такие сложности? В конце концов, мы прекрасно обходились функциями с разными именами. Отвечу так: классы типов &mdash; это способ говорить о *способностях* типов, а не об их устройстве. `Describable` не говорит нам ничего о том, из чего состоит тип, зато говорит, что тип умеет описывать сам себя. `Eq` не рассказывает о структуре данных, зато сообщает, что значения этого типа можно сравнивать. Это чрезвычайно мощная идея, ведь она позволяет писать функции, которые требуют от типа лишь минимально необходимого набора способностей &mdash; не больше и не меньше.

И вот тут мы подходим к самому интересному. Помните, в прошлой главе я говорил про этажи нашего типового небоскрёба &mdash; `Maybe`, списки, `IO`? Так вот, оказывается, у самих конструкторов типов тоже бывают способности, которые можно выразить через классы типов. И первая такая способность, с которой нам предстоит познакомиться, называется `Functor`.

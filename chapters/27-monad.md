# Монада

Вот мы и добрались до слова, которое пугает многих новичков в Haskell больше, чем любое другое. &laquo;Монада&raquo; &mdash; звучит почти как заклинание из какого-то тайного ордена. Спешу вас успокоить: ничего мистического здесь нет, это всего лишь ещё один класс типов, третий и последний в нашей маленькой трилогии про способности этажей. Мы уже подготовили для него всю необходимую почву, так что бояться нечего &mdash; идём дальше.

## Этаж внутри этажа

Напомню, на чём мы остановились. У нас была функция:

```haskell
half :: Int -> Maybe Int
half x
  | even x    = Just (x `div` 2)
  | otherwise = Nothing
```

И когда мы попытались применить её через `fmap` к значению `Just 40`, то получили не `Maybe Int`, а `Maybe (Maybe Int)`:

```haskell
Prelude> fmap half (Just 40)
Just (Just 20)
```

Почему так вышло? Присмотримся к сигнатуре `fmap` ещё раз:

```haskell
fmap :: (a -> b) -> f a -> f b
```

Здесь `b` может быть *чем угодно*, в том числе и снова значением на этаже `f`. Компилятору совершенно неважно, что `half` сама возвращает `Maybe Int` &mdash; для `fmap` это просто очередной тип `b`, и она честно заворачивает его в ещё один слой `f`. В результате мы получаем два вложенных `Just`, дом с этажом внутри этажа, и это неудобно: чтобы добраться до числа `20`, нам пришлось бы дважды разбирать конструктор `Just`.

А теперь представим, что нам нужно применить `half` не единожды, а дважды подряд:

```haskell
halfTwice :: Int -> Maybe (Maybe (Maybe Int))
halfTwice x = fmap half (half x)
```

С каждым новым применением этажи громоздятся друг на друга, как матрёшка. Ясно, что так продолжаться не может &mdash; нужен способ не просто применить функцию, возвращающую этаж, но и тут же &laquo;расплющить&raquo; результат в один-единственный этаж.

## Оператор `>>=`

Именно эту задачу решает класс типов `Monad`:

```haskell
class Applicative m => Monad m where
    (>>=) :: m a -> (a -> m b) -> m b
```

И снова обратим внимание на суперкласс: всякая монада обязана прежде быть аппликативным функтором (а значит, и просто функтором). Это не случайно &mdash; `Monad` не заменяет собой `Functor` и `Applicative`, а достраивает их, добавляя ровно одну новую способность.

Оператор `>>=` называют &laquo;бинд&raquo; (от англ. bind, &laquo;связать&raquo;), и его сигнатура заслуживает пристального разбора:

```haskell
(>>=) :: m a -> (a -> m b) -> m b

        значение   функция,       результат,
        на этаже m которая       снова на
                   САМА порождает одном
                   этаж m         этаже m,
                                  а не двух!
```

Ключевое отличие от `fmap` в том, какую функцию мы применяем: не `a -> b`, а `a -> m b`. То есть функция, переданная в `>>=`, изначально знает, что порождает новый этаж, и `>>=` умеет этот новый этаж не громоздить поверх старого, а слить с ним воедино.

Определим представителя `Monad` для `Maybe`:

```haskell
instance Monad Maybe where
    Nothing >>= _ = Nothing
    Just x  >>= f = f x
```

Читается на удивление просто: если исходное значение &mdash; пустышка, то и результат &mdash; пустышка, функцию `f` даже вызывать не будем. А если внутри `Just` есть значение `x`, мы просто берём и применяем к нему `f` напрямую, без какого-либо дополнительного заворачивания &mdash; ведь `f` сама уже возвращает `Maybe b`, а не голое `b`, и заворачивать тут попросту нечего.

Перепишем наш пример с двойным делением пополам:

```haskell
halfTwice :: Int -> Maybe Int
halfTwice x = half x >>= half
```

```haskell
Prelude> halfTwice 40
Just 10
Prelude> halfTwice 41
Nothing
Prelude> halfTwice 42
Nothing
```

Обратите внимание на последний пример: `42` &mdash; чётное число, `half 42` даст нам `Just 21`, но `21` &mdash; уже нечётное, и `half 21` вернёт `Nothing`. `>>=` аккуратно пронёс это `Nothing` до самого конца, ни разу не заставив нас вручную проверять, не провалилось ли вычисление на промежуточном шаге. Ни один этаж не громоздится поверх другого &mdash; на каждом шаге мы остаёмся ровно на одном этаже `Maybe`.

## Цепочки вычислений

Настоящая сила `>>=` раскрывается, когда шагов не два, а много:

```haskell
process :: Int -> Maybe Int
process x = half x >>= half >>= half
```

```haskell
Prelude> process 80
Just 10
Prelude> process 100
Nothing  -- 100 -> 50 -> 25, а 25 уже нечётное
```

Каждое звено цепочки может провалиться, и если это случится, вся цепочка дальше просто не выполнится &mdash; результат `Nothing` пронесётся через все оставшиеся `>>=`, не вызывая ни одной из последующих функций. Это удивительно похоже на короткое замыкание в булевых выражениях (`False && что-угодно` сразу даёт `False`, не вычисляя правую часть), только тут короткое замыкание работает на уровне целых вычислений, а не отдельных значений.

Именно эта особенность и делает `Maybe`-монаду такой ценной: она избавляет нас от бесконечных проверок &laquo;а не `Nothing` ли у меня на руках?&raquo; после каждого шага. Мы просто описываем последовательность действий, а забота о распространении неудачи целиком ложится на плечи `>>=`.

## До-нотация

Цепочка из нескольких `>>=` подряд, да ещё и с лямбдами, быстро становится трудночитаемой:

```haskell
lookupUser :: Int -> Maybe User
lookupAddress :: User -> Maybe Address
lookupCity :: Address -> Maybe String

findCity :: Int -> Maybe String
findCity userId =
    lookupUser userId >>= \user ->
    lookupAddress user >>= \addr ->
    lookupCity addr
```

Для таких цепочек в Haskell предусмотрен специальный синтаксический сахар &mdash; так называемая до-нотация (англ. do-notation), уже знакомая нам по главе про `IO`. Да-да, тот самый `do`, которым мы пользовались, когда писали `main`, &mdash; это вовсе не что-то особенное для ввода-вывода, это универсальный синтаксис для любой монады:

```haskell
findCity :: Int -> Maybe String
findCity userId = do
    user <- lookupUser userId
    addr <- lookupAddress user
    lookupCity addr
```

Выглядит почти как обычный императивный код, не правда ли? Строчка за строчкой, будто бы последовательность действий. Но не обманывайтесь: за кулисами компилятор честно превращает этот `do`-блок обратно в цепочку `>>=`, полностью эквивалентную той, что мы писали руками чуть выше. `<-` внутри `do`-блока читается как &laquo;извлеки значение из этажа и дай ему имя&raquo;, а не как настоящее присваивание &mdash; и если на каком-то шаге получится `Nothing`, вся оставшаяся часть блока просто не выполнится.

Вот теперь-то и открывается тайна `IO`, которую я обещал раскрыть ещё в главе про этажи. `IO` &mdash; тоже монада:

```haskell
main :: IO ()
main = do
    putStrLn "Как вас зовут?"
    name <- getLine
    putStrLn ("Приятно познакомиться, " ++ name ++ "!")
```

Каждая строчка внутри `main` &mdash; это шаг вычисления на этаже `IO`, и `>>=` (спрятанный внутри `do`) последовательно связывает их друг с другом, гарантируя, что взаимодействие с внешним миром происходит строго в том порядке, в каком мы его описали. Вот почему, кстати, из `IO`-этажа нельзя просто взять и &laquo;выйти&raquo; &mdash; в отличие от `Maybe`, где мы вольны в любой момент через паттерн матчинг извлечь значение и остаться на первом этаже, `IO` не предоставляет никакой безопасной лазейки наружу. Единственный путь &mdash; это `>>=` и `do`, шаг за шагом, оставаясь на одном и том же этаже вплоть до самого завершения программы. Помните, в главе про конструктор типа я говорил: &laquo;есть такие этажи, оказавшись на котором, мы в конечном итоге обязаны на него и вернуться&raquo;? Вот теперь вы знаете, о чём шла речь.

## Монада тоже аппликативна и функториальна

Раз `Monad` &mdash; надстройка над `Applicative`, вполне логично, что через `>>=` можно выразить и `fmap`, и `<*>`. В самом деле, стандартная библиотека так и поступает:

```haskell
fmap f mx = mx >>= \x -> pure (f x)

mf <*> mx = mf >>= \f -> mx >>= \x -> pure (f x)
```

Присмотритесь: `fmap` через `>>=` берёт значение `x` с этажа, применяет к нему `f`, и полученный результат снова &laquo;поднимает&raquo; на этаж через `pure`. А `<*>` делает практически то же самое, только дважды &mdash; сперва достаёт функцию `f`, затем значение `x`. Это лишний раз подтверждает наблюдение, которое мы делали на протяжении всей этой маленькой трилогии: `Functor`, `Applicative` и `Monad` &mdash; не три разрозненные идеи, а три последовательно усиливающиеся способности, каждая следующая &mdash; строго мощнее предыдущей.

```
   Functor         обычная функция  ->  значение на этаже

   Applicative      упакованная функция -> упакованное значение

   Monad            функция, порождающая новый этаж,
                     да ещё и умеющая слить этажи воедино
```

Если `Functor` умел лишь &laquo;достать, применить, положить обратно&raquo;, а `Applicative` научился применять функцию, которая уже была на этаже, то `Monad` пошла ещё дальше: она умеет строить цепочки вычислений, каждый шаг которых сам решает, оставаться ли на этаже, или же прервать всю цепочку. Это и есть, пожалуй, главная сверхспособность монад &mdash; возможность управлять *последовательностью* и *исходом* вычислений прямо из недр самого типа, без единого `if`, без единой ручной проверки.

## Законы монады

Как `Functor` и `Applicative`, `Monad` подчиняется собственному негласному контракту. Приведу лишь самый показательный из законов &mdash; закон левой единицы:

```haskell
pure x >>= f  ==  f x
```

Если мы поднимем голое значение `x` на этаж через `pure`, а затем тут же &laquo;развяжем&raquo; его через `>>=` с функцией `f`, результат должен в точности совпадать с прямым вызовом `f x`. Иначе говоря, `pure` обязана быть настолько нейтральной операцией, что оборачивание и немедленное разворачивание не должно ничего менять по существу. Это правило, при всей своей простоте, отсекает великое множество некорректных, хотя формально типобезопасных реализаций &mdash; ровно так же, как законы функтора отсекали &laquo;функторов&raquo;, ломающих `Nothing` на случайный мусор.

## Небоскрёб обжит

Вот мы и завершили наше путешествие по типовому небоскрёбу, начатое ещё несколько глав назад. Мы научились подниматься на этажи через конструкторы типов, научились наделять типы общими способностями через классы типов, и, наконец, освоили три главные способности любого уважающего себя этажа: быть функтором, быть аппликативным функтором и быть монадой. Теперь, глядя на любую незнакомую конструкцию вроде `Either e a`, `[a]` или `IO a`, вы будете точно знать, какой инструментарий стоит попробовать в первую очередь &mdash; `fmap`, `<*>` или `>>=` &mdash; вместо того чтобы городить очередной вложенный паттерн матчинг.

Разумеется, тема монад этим не исчерпывается &mdash; впереди у нас ещё встреча с монадой `Either`, с монадическими трансформерами, с классом `MonadFail` и многим другим. Но фундамент заложен, и заложен он крепко. А значит, самое время двигаться дальше.
